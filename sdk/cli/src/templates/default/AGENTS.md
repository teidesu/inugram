# Inugram plugin workspace

This project builds TypeScript plugins for Inugram's QuickJS runtime. Each plugin
ships as one readable `.inu.js` script with a generated manifest header.

## Layout

- `inu.config.ts`: plugin entries, manifests, grants, and build configuration.
  Runs in Node; plugin code does not.
- `src/<plugin>/index.ts`: a plugin's entry point. `hello` is the starter example.
- `src/shared/`: reusable source. Each plugin bundles its own copy and runs in an
  isolated engine; module state is not shared between plugins.
- `dist/<plugin>.inu.js`: generated output. Edit sources and config, then rebuild.
- `tsconfig.json`: extends the plugin SDK's runtime types; checks `src`.

Add plugins under `src/` and register their entries in `inu.config.ts`. Follow the
existing `.js` extension convention for relative TypeScript imports.

## API reference

Read the installed SDK before using an unfamiliar API. Do not invent members,
grants, TL fields, or globals, or hide missing APIs with `any` casts.

Under `node_modules/@inugram/plugin-types/`:

- `common.d.ts`: primary contract, globals, lifecycle, limits, and `@needs-grant` tags.
- `grants.json`: valid permissions and scopes.
- `android.tl.d.ts`: Telegram objects and RPC methods for this SDK version.
- `android.jvm.d.ts`, `android.xposed.d.ts`, `android.notification-center.d.ts`:
  Android bridge APIs, threading, handles, and compiled routines.
- `canvas.d.ts`, `fs.d.ts`: drawing and filesystem APIs.

CLI usage lives in `node_modules/@inugram/cli/README.md` and `pnpm exec inu --help`.
Use the installed versions as the reference; app and SDK compatibility matters.

## Runtime and permissions

- `inu` and the declared runtime globals are available without imports. This is
  neither Node nor a browser: no DOM, Node built-ins, `process`, or `Buffer` unless
  explicitly provided by the SDK. Do not add DOM or Node types to plugin code.
- Dependencies bundled into plugin code must work in this runtime. Ask before
  adding a dependency; do not assume an npm package's runtime is available.
- Keep bundles readable and preserve the CLI's script format and manifest banner.
  Do not handwrite manifest headers or bypass the routine compiler.
- Update `manifest.grants` with API changes. Request only the required grants and
  scopes; check `@needs-grant` on every API used. Prefer public plugin APIs over
  `unsafe.jvm` or `unsafe.xposed` when they cover the task.
- Preserve manifest `name` and `author` unless intentionally changing plugin
  identity: together they determine whether an install updates an existing plugin.
- Initialize from the entry point. Use `inu.onUnload` for cleanup; its async
  handlers share a two-second window. Dispose registrations and release resources
  according to their API contracts; do not retain handles beyond their lifetime.
- Keep synchronous callbacks short, handle rejected async work, and follow each
  API's queue/thread rules. App UI may be unavailable when a plugin runs.
- Use `inu.kv` for persistent plugin settings, following `src/shared/storage.ts`.
  Do not substitute browser storage or Node filesystem APIs.

## JVM and Xposed routines

- Write direct `inu.jvm.routine(function (...) { ... })` or
  `inu.xposed.routine(function (ctx) { ... })` calls. The CLI compiles their bodies;
  calling an alias or passing a separately declared function is not equivalent.
- A routine is a restricted language compiled to a custom IR and running on the calling JVM thread, not a JS
  callback. Read the installed routine declarations before choosing syntax or
  assuming JS arithmetic, object access, or closure semantics.
- Captures are snapshots taken when the routine is constructed. Capture supported
  values through stable bindings; routine bodies cannot call JS helpers or `inu`.
- Use a function expression when a JVM routine needs its receiver through `this`.
  Xposed routines use their context parameter and answer through its setters.
- Compile through `pnpm build`; typechecking alone does not validate the routine
  subset. Do not edit generated bytecode or recorded source in `dist`.

## Checks and device work

After code or manifest changes, run:

```sh
pnpm typecheck
pnpm check
pnpm build
```

`check` validates manifests; it does not typecheck or run plugins. Run relevant
tests if the project adds them. Report checks actually run and any blockers.

`pnpm dev <plugin>` builds, pushes to a connected Android device, and reloads on
changes. It requires a running app with plugin developer mode enabled and skips
the install permission sheet. Use it when device deployment is requested; local
checks do not require it. Use `--app desu.inugram.beta` for the debug app and
`-s <serial>` to select a device. Do not uninstall plugins as part of verification.
